# ТЗ-03: Firebase Rules - точечное усиление без поломки пользователей

## Цель

Убрать явно лишние права записи в Firebase Rules, но не сломать регистрацию, гостевой доступ и owner-доступ.

## Важно перед началом

По правилам проекта перед изменением `firebase.rules.json` нужно получить явное подтверждение владельца.

Это ТЗ нельзя выполнять молча.

## Файл

- `firebase.rules.json`

## Задача 1: проверить `test_photos`

Нужно понять, используется ли путь `test_photos` в production.

Возможные решения:

- Если путь не нужен - закрыть запись полностью.
- Если нужен только владельцу - разрешить запись только owner UID.
- Если нужен приложению - ограничить запись владельцем конкретной записи, а не `auth != null` для всех.

Нельзя просто удалить правило без проверки использования.

## Задача 2: ограничить `diagnostics/runtime`

Нужно понять, кто должен писать runtime diagnostics.

Возможные решения:

- Только Cloud Functions.
- Только owner UID.
- Только authenticated user в свой собственный подпуть, если диагностика нужна от клиентов.

Нельзя оставлять общий write для всех non-anonymous пользователей, если записи попадают в общий лог.

## Задача 3: проверить профильные заявки и cooldown

Если в правилах есть возможность повторять запрос после отказа без ограничений, добавить защиту только если она не ломает нормальное повторное обращение.

## Проверка

- Owner UID сохраняет доступ.
- Новый пользователь может пройти регистрацию или гостевой flow.
- Обычный пользователь не может писать в чужие диагностические или тестовые записи.
- Приложение не падает из-за запрета диагностики.

## Что не делать

- Не закрывать все пути owner-only без анализа.
- Не менять `user_roles`, `security_config`, `authorized_devices` без отдельного согласования.
- Не ломать локальный owner-доступ.
