# ТЗ-06: Особый подход - где нельзя исправлять механически

## Цель

Зафиксировать пункты аудита, с которыми нельзя работать по принципу `просто запретить`. Эти места требуют осторожного решения, чтобы не сломать новых пользователей и доступ владельца.

## 1. Owner/admin email bypass

### С чем я не согласен

Я не согласен с идеей просто удалить email-путь владельца из `admin-panel/src/services/authService.ts`.

### Почему

В проекте есть прямое правило: сохранить `VITE_ADMIN_SERVICE_EMAIL`, `isPrimaryServiceEmail` и стабильный owner-доступ. Если удалить email-путь без замены, владелец может потерять вход в админку.

### Правильный подход

- Сначала подтвердить UID владельца.
- Сохранить `VITE_ADMIN_SERVICE_EMAIL` как fallback или как часть owner recognition, пока новая схема не проверена.
- Усиливать доступ через UID/server rules/custom claims, но не ломать текущий рабочий путь.

## 2. Автоматический Google redirect в admin-panel

### С чем я не согласен

Я не согласен с агрессивным автоматическим `signInWithRedirect` при каждом открытии без защиты от циклов.

### Почему

Можно получить бесконечный redirect loop, особенно если вошел чужой аккаунт или Firebase возвращает ошибку.

### Правильный подход

- Google-only вход можно сделать.
- После отказа показывать `Доступ запрещен`, а не снова редиректить.
- Хранить состояние `redirect in progress`.

## 3. Новые пользователи и device blocking

### С чем я не согласен

Я не согласен с резким включением жесткой блокировки так, чтобы новый пользователь вообще не попадал в приложение.

### Почему

Это может создать массовую проблему: новые пользователи будут застревать до одобрения устройства или заявки.

### Правильный подход

- Заблокированные устройства действительно блокировать.
- Новые или ожидающие пользователи должны попадать в guest mode.
- Guest mode должен закрывать только чувствительные разделы: контакты, анкеты, бизнесы.

## 4. Firebase Rules owner-only для всех спорных путей

### С чем я не согласен

Я не согласен с механическим закрытием всех подозрительных путей только на owner UID.

### Почему

Некоторые пути могут использоваться приложением для диагностики, регистрации, тестов или пользовательских действий.

### Правильный подход

- Сначала найти реальные обращения к пути в коде.
- Потом выбрать минимальное правило: owner-only, own-record-only или Cloud Functions-only.

## 5. Удаление fallback `uid` в media owner check

### Где нужен особый подход

Сама идея правильная: использовать только `userId`. Но если в базе уже есть старые записи только с `uid`, пользователи могут потерять доступ к своим старым медиа.

### Правильный подход

- Проверить, есть ли старые записи без `userId`.
- Если есть, сделать миграцию данных или отдельный одноразовый repair script.
- Не оставлять runtime fallback навсегда.

## 6. Перенос всех admin operations на Cloud Functions

### Где нужен особый подход

Идея правильная, но это нельзя делать одним большим изменением.

### Почему

Можно сломать всю админку сразу и сложно будет понять причину.

### Правильный подход

- Переносить по одному сервису.
- Сначала moderation, потом security controls, потом devices, потом trust tree.
- После каждого шага проверять owner/admin/moderator сценарии.

## Итоговое правило для будущего ИИ

Если исправление усиливает безопасность, но может заблокировать владельца или новых пользователей, нельзя применять его механически. Нужно выбрать вариант, где:

- Owner сохраняет доступ.
- Новый пользователь получает guest mode, а не тупик.
- Сервер не доверяет клиентскому UID.
- Firebase Rules не становятся набором лишних запретов без понимания реального flow.
