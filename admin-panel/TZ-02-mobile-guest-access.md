# ТЗ-02: Mobile App - гостевой доступ вместо зависания на поручителе

## Цель

Сделать так, чтобы новый пользователь без одобренной заявки не зависал на экране поручителя, а попадал в приложение с ограниченными правами.

## Главный принцип

Новые пользователи не должны получать полный доступ, но и не должны упираться в тупик. Для них нужен понятный гостевой режим.

## Файлы для анализа

- `src/components/AppAccessGuard.tsx`
- `src/components/SoftInviteAccessGate.tsx`
- `src/contexts/TrustedAccessContext.ts`
- `src/navigation/RootNavigator.tsx`
- экраны разделов: контакты, анкеты, бизнесы

## Задача 1: безопасный default в `TrustedAccessContext`

Нужно:

- Изменить default `isTrusted` с `true` на `false`.
- Проверить места, где `useContext(TrustedAccessContext)` может использоваться вне провайдера.

Ожидаемое поведение:

- При сбое провайдера пользователь не получает полный доступ автоматически.

## Задача 2: ввести или использовать статус гостя

Нужно определить единый смысл статуса:

- `approved`, `whitelist`, `temporary_access` - полный доступ.
- `pending`, `pending_sponsor`, `needs_manual_review`, отсутствие заявки - гостевой доступ.
- `denied`, `blocked` - экран отказа или блокировки.

Можно использовать название `guest_access`, если это не ломает существующую структуру. Если статус добавлять рискованно, можно вычислять гостевой режим на клиенте из существующих статусов.

## Задача 3: ограничить разделы для гостя

Гость не должен видеть или открывать:

- Контакты.
- Анкеты и профили пользователей.
- Бизнесы Чайки.

При попытке входа показать понятный экран:

`Для просмотра этого раздела нужна одобренная заявка`.

На экране должна быть кнопка подачи или просмотра заявки.

## Задача 4: убрать тупик на поручителе

Нужно:

- Не заставлять пользователя бесконечно оставаться на экране поручителя.
- Дать возможность продолжить в ограниченном режиме.
- Сохранять понятный путь к подаче заявки.

## Проверка

- Новый пользователь без заявки входит в приложение как гость.
- Гость не открывает контакты, анкеты, бизнесы.
- Пользователь с `approved` получает полный доступ.
- Пользователь с `denied` не получает гостевой обход отказа.
- При ошибке загрузки access state полный доступ не выдается автоматически.

## Что не делать

- Не блокировать всех новых пользователей полностью.
- Не переносить admin-panel auth в это ТЗ.
- Не менять Firebase Rules без отдельного ТЗ и согласования.
